# PM 프로젝트 실행 연결

2026-09-30 대표가 승인한 후속 구현. 공통 업무 지침을 실제 조사·개발·검수·재작업으로 연결한다. 기존 조직 UI 관리와 과거 정기 회차·재고 정책 데모는 보존한다.

## 실행 구조

`office/projects.py`의 부모 미션은 대표 원문 목표와 전체 완료 기준을 보존한다. PM은 읽기 전용 구독 실행으로 다음 한 단계를 판단한다. 서버가 허용된 직원과 실행 모드로 자식을 만들며, 자식 결과가 도착하면 자동으로 PM 검수를 대기열에 넣는다. 한 번에 한 직원만 실행한다.

- `research`: 공개 검색이 연결된 R&D·마케팅·영업에 조사 배정.
- `develop`: R&D에 등록된 공급망 GIS 프로필의 격리 파일 개발 배정.
- `draft`: 제공된 근거로 분석·내부 초안 작성.
- `revise`: `target_child_id`로 같은 프로젝트의 종료된 미대체 업무를 지정해 수정. 현재 작업뿐 아니라 이전 미달 업무도 선택할 수 있다. 원본 보고와 미달 기준은 보존하고 새 업무가 이를 대체한 계보를 남긴다.
- `request_input`: 필수 내부 자료의 질문·필요 이유·검토한 대안을 저장. 업무 상세의 답변 폼으로 답하면 같은 프로젝트가 이어진다. 자료가 없다는 답변도 PM에게 전달한다.
- `accept`: 원래 전체 기준과 지표를 검수. 일부 결과·보고서 도착만으로 완료하지 않는다.
- `blocked`: 현재 범위로 풀 수 없는 문제를 남긴다.

일반 배정의 `criteria`는 해당 단계의 완료 기준이다. 전체 `goal_criteria`는 별도 보존된다. 조사업무에 개발 완료 기준을 잘못 붙였으면 PM이 이유와 함께 해당 작업 기준을 정정해 재작업시킬 수 있으나, 최종 목표를 줄일 수는 없다. 독립적인 다른 업무는 진행할 수 있지만 미달 업무를 숨기고 전체 완료할 수는 없다. 다른 프로젝트·이미 대체된 업무를 재작업하거나 근거 없이 완료하는 판단은 서버가 거절하고 제한된 횟수 안에서 PM에게 재판단시킨다.

## 접수와 개입

`POST /api/org/missions`에서 `employee_id=das-pm`, `execution_mode=project`, `context.project_id=daslab-growth`를 사용한다. `project_profile`은 `research-deliverable-v1` 또는 `supply-network-gis-v1`이다. 화면에서 PM·비서에게 평소 말로 맡긴 업무도 기본적으로 프로젝트로 연결하므로 내부 양식을 채울 필요가 없다. 명시적인 기존 조직 UI 수정·반영과 전문 직원 직접 배정·명시한 단일 실행은 기존 경로를 쓴다. 공급망 프로필 선택과 UI 대상 구분은 초기 규칙이며 AI 의도 분류의 완성이 아니다.

자료 답변은 `POST /api/org/missions/{id}/input`으로 `input_round`와 `{question_id: text}` 형태의 `answers`를 받는다. 같은 질문 회차·같은 답변은 중복 실행하지 않으며 오래된 회차나 다른 답변은 거절한다. 중지·취소·추가 지시는 부모와 현재 자식에 함께 적용된다. 서버 재시작은 기존 정책대로 진행 중인 일을 일시 정지하고, 재개 시 저장된 단계와 자식을 이어간다.

## 작업본과 검수

새 공급망 프로필의 작업본 계보 키는 부모 미션 ID와 `supply-network-gis-v1`이다. 다른 프로젝트나 기존 재고 프로필의 최신 파일을 자동 상속하지 않는다. 상속 전후 파일 해시를 대조하고, PM 수용 직전에도 실제 산출물 해시와 프로필을 확인한다.

PM 판단과 공개 화면의 부모 데모 정보는 같은 프로젝트의 최신 개발 업무 영수증에서 읽는다. 후처리 성공 뒤 부모에 남은 옛 실패 복사본을 현재 결과와 함께 보여 주지 않으며, 이전 실패 자체는 원본 실행 이력에 보존한다. 최신 개발이 실패했을 때 이전 성공으로 대체하거나 검수 통과만으로 전체 목표를 수용하지 않는다.

프로젝트 공급망 데모 개발은 `config/projects.json.prototype_timeout_seconds=900`으로 최대 15분 실행한다(설정 상한 30분). PM 판단·조사·일반 업무와 기존 재고 데모의 제한 시간은 기존 설정을 유지한다. 파일 작성 뒤 정적 검사나 보고가 실패해도 안전한 6개 파일을 별도 해시로 고정해 같은 프로젝트의 재작업에 전달하며, 실패 이력을 완료로 바꾸지는 않는다.

이 기능 이전에 실패한 작업본은 운영자가 현재 6개 파일과 기준 파일의 해시를 확인한 뒤 `POST /api/org/missions/{id}/capture-prototype-repair`로 명시적으로 고정할 수 있다. 모든 실행이 멈추고 부모 PM이 일시 정지·막힘일 때만 허용한다. 이는 실패 이후 확인한 현재 파일의 보존이며 원래 실행 종료 시점의 바이트 동일성·코드 동작 검증이 아니다. 원래 실패 기록은 유지하고, 새 재작업도 기존 정적·모델·브라우저 검사를 거쳐야 한다.

최종 파일은 각각 500,000바이트, 6개 전체는 1,000,000바이트 이하다. 긴 검증 기록으로 실패한 README만 재작업 자료 수집·상속에서 전체 한도 안으로 임시 보존한다. 코드 파일과 최종 검사·미리보기 한도는 늘리지 않는다. 직원에게 최종 크기와 허용 모듈, 간결한 결과 기록 방법을 명시적으로 전달한다.

`office/network_prototypes.py`는 로컬 GIS 좌표·시설입지·용량 배분·불확실성 배송 모델의 합성 기초 계약이다. 이것만으로 산업 문제를 조사했거나 고객 데모를 납품한 것이 아니다. R&D는 선정 문제를 실제 모델·화면 소스에 반영해야 하며 README만 수정한 결과는 개발 완료로 인정하지 않는다.

`office/network_checks.py`는 독립적인 Python 거리·시설 부분집합·잔여 네트워크 흐름 계산, 원시 배송/비용 기록과 KPI, 동일 시드 비교, 경계조건 및 브라우저 지도·표시 지표를 대조한다. 기존 재고 프로필 검사는 유지한다. 기술 검사 통과와 고객 현장 효과·사업 성과는 구별한다.

정상 종료한 직원의 후처리 오탐은 기존 `recheck-prototype` 경로로 원본 파일을 바꾸지 않고 재검사할 수 있다. 공급망 프로젝트는 멈춘 같은 부모·프로필과 고정된 파일/기준 해시를 확인한 뒤 `NetworkVerifier`를 사용한다. 재고 데모의 정책 비교 검사를 대신 통과시키지 않는다. 원본 실패와 새 검수 영수증을 구분하며 호스트에서 생성 테스트를 실행하지 않는다.

## 운영 한도와 남은 범위

`config/projects.json`은 프로젝트별 자식 8개, PM 판단 14회, 같은 업무 계보별 재작업 2회로 제한한다. 재작업 횟수는 서버가 같은 프로젝트의 `supersedes` 연결을 따라 계산한다. 조사 업무를 두 번 수정했어도 이후 개발 업무에는 별도의 수정 기회가 있지만, 전체 자식·판단 한도는 그대로 적용한다. 다른 프로젝트의 원본이나 순환·누락된 계보는 거절한다. `workflow.round`는 프로젝트 전체 재작업 누계와 화면 보고용으로 유지하며 한도를 초기화하지 않는다. 최종 완료에는 대체되지 않은 모든 업무의 충족과 기존 파일·브라우저 검증이 계속 필요하다.

전체 구독·일일 실행 한도를 함께 사용한다. 운영자가 명시하는 `--extra-runs-today 1..30`은 승인된 다단계 검증에 필요한 당일 임시 추가 한도다. 기본 일일 10회·기존 사용 이력을 바꾸지 않으며 한국 날짜 변경이나 옵션 없는 재시작 때 종료된다. 직원이 스스로 늘릴 수 없고 유료 API로 전환하지 않는다.

기존 정기 회차는 고정 조사·초안·PM 사후 검토 경로로 유지한다. 새 프로젝트 실행은 별도 접수이며 정기 일정을 몰래 교체하지 않는다. 외부 게시·고객 연락·설치·공개 배포·다른 저장소 개발·다중 PM/임시 직원·상시 모니터링은 이번 구현에 포함하지 않는다. 실제 구독 실행 결과는 별도 검증 기록으로 남긴다.
