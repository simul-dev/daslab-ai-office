# PM 프로젝트 실행 검증 · 2026-09-30

대표의 ‘그럼 해’ 지시에 따른 실행 연결과 실제 첫 프로젝트의 검증 기록이다. 구현 범위는 [프로젝트 실행 문서](PROJECT-WORKFLOW.md)를 따른다. 운영 DB·원시 실행 로그·인증 정보는 Git에 넣지 않는다.

## 구현과 회귀 검사

- 기존 조직 미션·직원·구독 실행 대기열을 재사용해 PM 판단 → 실제 직원 배정 → 결과 도착 → PM 검수·재작업을 연결했다.
- 원래 대표 목표와 단계별 완료 기준을 분리했다. 전체 목표를 조사 보고서로 축소하거나 미달 업무를 숨긴 완료는 거절한다.
- 실제 저장된 조사 입력에 PM과 같은 개발 규격을 전달한다. 다른 프로젝트의 작업본 상속, 보고·개발 파일의 검수 후 변조, 오래된 질문 답변과 늦게 도착한 취소 결과를 거절한다.
- 테스트용 별도 서버에서 질문·필요 이유·대안을 표시하고 답변 폼으로 입력한 뒤 R&D 실행과 PM 검수가 자동으로 이어지는 화면을 확인했다. 이는 가짜 직원의 시험 자료이며 실제 회사 성과가 아니다. 로컬 화면 근거는 `test-results/project-ui/input-resumed.png`다.
- 전체 `python -m unittest discover -s tests`: 485개 실행, 481개 통과·4개 건너뜀(207.8초). 이후 최신 검수 결과 표시 보정은 프로젝트 검사 29개(신규 3개 포함)를 별도로 통과했다. `node --check static/office.js`와 `git diff --check`도 통과했다.
- 재작업 한도는 업무 계보마다 2회이며 전체 배정·PM 판단·일일 실행 한도는 별도 유지한다. 조사에서 재작업을 했다고 개발의 첫 오류 수정을 막지 않는다. 대체된 옛 실패는 현재 직원 상태에서 제외하되 상세 이력에서는 당시 결과를 보존한다.
- 정적 검사·보고 형식 실패 뒤에도 같은 프로젝트의 안전한 6파일을 고정해 다음 수정에 전달한다. 시험용 직원으로 실제 문법 오류 → 작업본 상속 → 수정 → 기존 검수 경로를 확인했다. 파일·기준 파일 변조, 다른 프로젝트, 추가 파일, 하드링크와 검수 중 변경은 재작업 원본으로 승인하지 않았다.

## 공급망 모델 검사기

등록된 새 프로필은 기존 재고 정책 데모와 분리된다. 위경도 지도, 후보 거점 부분집합 비교, 정수 용량 제약의 최소비용 물량 배분, 같은 주문 외생 지연을 쓰는 시뮬레이션이 검사 대상이다. 소규모 합성 단일기간 모델이며 실제 도로·고객 데이터·현장 효과를 뜻하지 않는다.

기초 소스에 대해 독립 Python 거리·최적화 계산과 원시 주문/비용 재집계, 알려진 작은 해, 0수요·용량 부족·장애·민감도·재현성, 실제 브라우저의 지도 좌표·연결·화면 숫자·모바일 등 17항목을 통과했다. 이 기초 소스 검사만으로 직원 개발이나 선정한 산업 문제의 완성을 주장하지 않는다.

실제 브라우저 결함 주입에서도 원시 주문은 그대로 두고 총비용을 0으로 바꾼 모델과, 내부 속성은 정상인데 사용자에게 보이는 지표만 999로 바꾼 화면을 각각 거절했다. 단위 검사에는 원시 모델 결함 18종과 지도·표시 결함 14종이 포함된다.

## 실제 구독 실행

부모 미션은 `c91b71b450c941b18e7d735c7e67fdf1`이다. 감독자가 자연어 목표를 한 번 접수했고 이후 직원 배정은 프로젝트 PM 판단에서 생성됐다. 공급망의 실전 문제 조사, 입지·네트워크 최적화, 불확실성 시뮬레이션, GIS와 상단 KPI 비교가 원래 목표다. 기존 재고 데모와 이력은 보존한다.

실제 실행 중 확인해 고친 문제:

1. PM이 조사 업무에 전체 개발·브라우저 완료 기준까지 붙였다. 전체 목표를 유지하면서 단계별 기준을 정하도록 판단 입력을 수정했다. 기존 연구 보고를 지우지 않고 PM이 조사 기준을 정정한 재작업을 배정했다.
2. PM에게만 제공된 `development_contract`가 조사 직원에게 전달되지 않았다. 직원은 확인 불가를 사실대로 보고했고 PM은 다음 지시에 규격을 직접 넣었다. 엔진도 PM과 직원에게 같은 규격을 자동 전달하도록 수정했다.
3. 첫 개발의 실제 재개 시도 `2dfbd43097484e09af14bbe43213f2bf`는 기존 600초 제한에 걸려 최종 보고 없이 실패했다. 모델·화면·테스트 파일을 포함한 46,622바이트의 작업본은 남았다. 기존 실패를 완료로 바꾸지 않고, 현재 확인한 파일을 별도 재작업 자료로 고정하는 운영 복구 경로를 마련했다. 새 프로젝트의 개발 실행만 900초로 제한하고 일반·기존 업무의 시간 제한은 유지한다.
4. 후속 개발 `f0ebf61cdf0446da9dd27129dac2629d`는 지역 배송망을 구현했지만 원시 결과 전체를 기록한 README가 652,628바이트로 파일당 500,000바이트 상한을 넘었다. 현재 6파일을 미검증 복구 자료로 보존하고 최종 검사는 그대로 유지했다. 감독자 코드 검수에서 금지 모듈 사용, 합성 출처 필드 누락, API·화면 기본 사례 불일치, 잘못된 입력 후 사례 변경의 오류 처리를 추가로 찾아 PM에게 전달했다. 이 개입을 PM이 처음부터 스스로 발견한 실적으로 계산하지 않는다.
5. PM이 배정한 두 번째 개발 재작업 `cc45b886986d430db222f9d38738995e`는 직원 실행과 보고서 검사를 정상 종료했다. 이후 정적 검사기가 `model.test.cjs`의 검색용 정규식 안에 있는 `require`를 실행 호출로 오인했다. 직원 파일을 변경하거나 재작업 한도를 늘리는 대신 검사기를 보정하고, 동일 해시의 기존 제출물을 프로필에 맞는 독립 검사로 재검수하는 경로를 연결했다. 원본 실패와 별도 재검수 판정은 각각 보존한다.
6. 재검수 성공이 자식 업무에 저장된 뒤에도 부모의 오래된 실패 영수증이 PM 맥락에 전달돼 PM이 상태 충돌을 이유로 보류했다. PM 판단과 공개 화면이 동일 프로젝트의 최신 개발 자식 영수증을 읽도록 보정했다. 실패 이력·기존 상태·실행 횟수를 지우거나 자동 수용하지 않는다. 최종 PM 검토에는 별도 브라우저 조작 관찰과 기존 재고 파일의 해시 대조 결과도 전달했다.

개발 도중 S2 수치 검증 사례가 기본 화면으로 쓰이며 지역망 사례가 사용자에게 연결되지 않은 점도 관찰했다. 검사용 작은 해와 업무용 데모의 목표 달성은 별도이며, PM 검수 지침에 이 구분을 추가했다. 파일 수정·테스트 통과만으로 사용자 기대 수준을 충족한 것으로 처리하지 않는다.

첫 PM 판단 `b91de7751b6940f393894c095b3f5ab6`, 원조사 미션 `efbb8875e61849509a6a007c50a16c30`, 수정 조사 `a348128d337b4c54a53f176627ca8f11`, 계약 전달 후 조사 `00c559726d204cc3af7ff8b3951cb2a7`을 보존한다. 중간 서버 수정 때 중지한 PM 시도도 취소 이력으로 남겼다.
