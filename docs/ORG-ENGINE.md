# 조직 운영 엔진 · 2026-09-29

이번 직접 지시는 조직·직원·기억·업무·실행·개입·성과를 연결하고, 실제로 조작할 수 있는 화면을 만드는 것이다. 음성은 사용자가 버튼을 눌러 선택하는 입력 수단이며 UI만으로 모든 기본 제어가 가능해야 한다. 9월 26일 별도 v0.4 계획과 CP0는 보존한다. 그 계획의 전체 사업 기능이나 Phase 1–5를 완료한 것으로 처리하지 않는다.

## 실행 구조

```text
대표 → 전용 비서 → DAS Lab PM → R&D / 기획·마케팅 / 영업지원
                    │
            직원·기억·업무·개입 원장
                    │
       우선순위 큐 → 직원별 실행 문맥 → 공식 Codex CLI
                    │                      │
             조직 화면 ← 실제 실행 이벤트·결과
```

- 직원은 영속 ID와 역할을 가진다. 필요한 업무가 들어왔을 때만 실행하며, 화면에 직원이 있다고 상시 LLM을 호출하지 않는다.
- 비서 접수와 최초 담당 배정은 현재 코드 규칙이다. 아래 조직 UI 작업에 한해 PM의 계획·검수 판단을 연결했다. 여러 사업을 스스로 운영하는 완전 자율 조직으로 표현하지 않는다.
- 각 실행에는 담당 역할, 프로젝트 지식, 직원 기억, 현재 업무, 이전 결과와 대표의 수정 지시를 전달한다.
- 일시정지·방향 수정·담당 변경 시 현재 시도를 중단한다. 실제 작업자가 종료된 뒤 정지 상태가 확정된다. 재개는 저장된 맥락을 이용한 새 실행이며 기존 추론을 같은 지점에서 이어가는 것은 아니다.
- 상태 변경은 조건 변수와 SSE 이벤트로 화면에 전달한다. 작업 배정을 위한 주기적 폴링은 없다. 서버 재시작 뒤 미완료 작업은 대표가 재개한다.

## 데이터와 실행 경계

새 DB는 `data/organization.sqlite3`이다. 기존 `data/office.sqlite3`와 실행 파일은 유지하며 `/legacy`에서 조회한다. 조직 엔진이 실행되는 서버에서는 이전 실행기 큐와 이전 미션 쓰기 API를 비활성화하여 구독 실행 한도가 따로 적용되는 것을 방지한다.

기본 실행기는 기존 구독으로 인증하는 공식 Codex CLI이고, 동시 1개·일일 상한·시도 상한을 적용한다. API 과금으로 전환하지 않는다. 기본 실행 능력은 제공된 문맥의 분석·문서·코드 제안이다. 2026-09-30부터 PM·R&D에는 아래 조직 UI 개발 범위를 연결했다. 일반 저장소 개발·공개 배포·SNS 발행·예약 실행·임시 직원 자동 생성·Claude 연결은 포함하지 않는다.

## 조직 UI 개발 위임 · 2026-09-30

- 대표의 직접 지시에 따라 `config/development.json`에서 DAS-PM·DAS-RD만 조직 UI 개발을 허용한다. 조직 화면의 지시에는 `office-ui` 대상 문맥을 전달한다. 공개 홈페이지는 브랜드 참고 자료이며 수정 대상이 아니다.
- 개발 실행은 HTML/CSS/JS·로고·브랜드 지침을 별도 작업 폴더에 복사해 연결한다. 공식 Codex CLI가 그 폴더에서 실제 파일·셸 도구를 사용한다. 운영 DB·서버·설정 수정 권한을 직원에게 주지 않는다.
- CLI 사용자 설정을 생략하므로 개발 실행에 작업 폴더 쓰기 프로필과 Windows sandbox 설정을 명시한다. 네트워크는 비활성화한다. [공식 권한 프로필](https://learn.chatgpt.com/docs/permissions), [Windows 설정](https://learn.chatgpt.com/docs/config-file/config-basic)을 따른다.
- 정적 검사·변경 해시를 통과한 작업본만 별도 loopback 미리보기로 제공한다. 미리보기는 실제 조직 상태를 조회하지만 업무 제출·개입·기억 수정은 막는다. 운영 디자인에 자동 적용하지 않는다.
- 코드 검사와 실제 브라우저 확인을 구분한다. 직원의 개발 실행기에 브라우저 권한을 주지 않고 서버의 별도 검사기가 기본 화면과 읽기 전용 동작을 확인한다. 미리보기 생성이나 기본 동작 검사만으로 디자인 품질 검증 완료를 주장하지 않는다. 자율 PM 회의·임시 하위 에이전트 생성은 아직 없다.

직원별 활동과 결과 보고를 집계하지만, AI 자기평가와 형식 검증만으로 검증된 사업 성과를 늘리지 않는다. 실행 시간으로 진척률을 만들지 않는다. 성과의 검증 수준과 모르는 값은 그대로 표시한다.

## 사용

### 미리보기 후속 작업과 반영 · 2026-09-30 보완

기존 디자인 개선본의 HTML/CSS를 운영 `static/`에 반영했다. 새 디자인을 다시 만들지 않았으며 기존 업무 기능의 JavaScript는 유지·보완했다. 운영 서버는 `/brand/`의 허용된 로고·이미지·폰트만 제공한다.

후속 개발은 `source_attempt_id`로 검증된 미리보기를 이어받고, 파일 해시를 접수 시와 실행 전에 다시 확인한다. “수정된 디자인”처럼 이전 결과를 가리키는 요청은 후보가 하나일 때 연결한다. 후보가 여럿이면 각 미리보기 상세에서 대상을 선택한다. 새 디자인 요청은 운영 소스에서 시작한다.

미리보기 상세의 “이 미리보기 반영”, “반영하고 커밋”, “반영·커밋·푸시”는 명시적 `delivery` 미션으로 처리한다. 모델에 재디자인을 요청하지 않는다. PM 관리가 켜진 상태에서 비서·PM에게 자연어로 맡긴 후속 지시는 아래 검수 흐름을 거친다. 실제 파일·Git 처리는 공통으로 `office/delivery.py`가 검증된 파일과 원래 운영본 해시를 받아 고정된 UI 경로만 반영한다. `config/development.json`의 허용 동작·원격 URL을 따르며 다른 로컬 변경, 기존 스테이징, 다른 미푸시 커밋, 원격 분기 변경은 보존하고 막힘으로 보고한다. 푸시는 같은 이름으로 연결된 기존 upstream 브랜치에 이 처리에서 만든 커밋만 보낸다. 강제 푸시는 없다.

파일 반영·커밋·푸시 단계 기록을 DB에 남겨 푸시 실패 후 재개가 커밋을 중복 생성하지 않게 했다. 서버 재시작 뒤에는 기존처럼 직접 재개한다. 강제 종료 뒤 남은 Git 잠금 파일은 자동 삭제하지 않는다. Git 처리는 구독 AI 실행 횟수에 포함하지 않는다. 완료 상태 `delivered`는 요청한 반영 처리의 완료이며 사업 성과를 뜻하지 않는다. 직접 반영 미션의 Git 기록과 PM 관리 미션의 브라우저 검사 기록을 구분한다. 직원의 네트워크·작업 폴더 제한은 유지한다.

미리보기 존재 여부와 미션 막힘 상태를 분리했다. 직원이 `blocked`로 보고한 이유를 미리보기 안내로 덮어쓰지 않으며, 이전 버전에서 `review`로 저장된 차단 보고도 서버 시작 시 `blocked`로 복원한다.

동일본이 이미 반영·커밋·원격 저장되어 있으면 다시 커밋하거나 푸시하지 않는다. 깨끗한 작업 트리, 정확한 작업본 바이트, Git 정규화 후 동일한 커밋 트리, 현재 브랜치와 upstream, 원격 커밋의 일치를 재확인하고 `already_synced`로 보고한다. 이때 `pushed`는 false이며 `remote_verified`와 `verified_commit`에 확인 결과를 남긴다. 기존의 미푸시 커밋을 대신 발행하지 않는다.

보존 파일을 관리자가 연결한 `preview_import`는 새 AI 실행이 아니다. 원본 파일·비교 기준·현재 파일 해시와 복구 근거를 따로 남기며, 구독 실행 횟수에 포함하지 않는다. 복구본도 해시 확인과 PM·브라우저 검수를 거쳐야 한다. 일반 미션 입력으로 복구 기록을 생성할 수 없다.

### PM이 맡는 배정·검수·재작업 · 2026-09-30 보완

`config/development.json`의 `managed_pm.enabled`가 켜져 있으면 비서·DAS-PM에게 맡긴 조직 UI 개발 요청을 부모 업무로 관리한다. `office/management.py`가 기존 단일 실행 큐에서 PM 계획 → DAS-RD 작업 → 브라우저 기본 동작 검사 → PM 검수 순서를 이어 간다. 기존 개선본의 반영 요청은 고정한 작업본 검사부터 시작한다. R&D에 직접 맡긴 요청과 명시적 반영 버튼은 기존 실행 경로를 유지한다.

PM 판단은 `office/pm.py`의 제한된 JSON 응답으로 계획·배정·수정 지시·수락·막힘을 제안한다. 실제 하위 업무 생성과 파일 처리는 서버가 수행한다. 담당 직원은 DAS-RD로 제한되며, 원래 요청과 대표의 추가 지시, 완료 기준, 이전 결과를 전달한다. 수정은 설정 범위 안에서 최대 두 번까지 연결하고 PM 판단 횟수와 구독 일일 한도도 적용한다. 대표가 요청한 반영·커밋·푸시만 검수 뒤 이어서 실행한다. PM의 판단 자체가 새 권한을 부여하지 않는다.

`office/browser_verification.py`는 고정한 미리보기 해시를 대상으로 별도 임시 브라우저를 열어 직원 화면·이미지·직원 선택·기억/성과 탭·PC/모바일 가로 넘침·기존 미션 상세 열기·브라우저 오류를 확인한다. 화면 저장은 검사 실행 폴더의 근거로 남는다. 요청·기억 저장·개입 같은 쓰기 동작, 외부 사이트 이동과 외부 연결은 허용하지 않는다. 이 검사는 시각적 완성도나 사업 성과 판정이 아니다.

검사기에는 선택 의존성 `requirements-browser.txt`의 Playwright와 사용 가능한 Chromium 브라우저가 필요하다. 설치된 Edge/Chrome을 사용할 수 있으며, 도구가 없거나 실행되지 않으면 검수 성공으로 넘기지 않고 막힘으로 보고한다. 의존성을 자동 설치하거나 유료 API로 전환하지 않는다.

전체 업무의 상세 화면에 현재 단계, 담당 직원의 하위 업무, 검사 결과와 막힘 이유를 모아 보여 준다. 정지·취소는 PM과 진행 중인 하위 작업에 함께 적용한다. 추가 지시는 작업을 정지하고, 재개할 때 PM이 다시 계획한다. 부모 업무의 PM을 다른 직원으로 바꾸거나 하위 업무를 별도로 제어하지 않는다. 파일·Git 반영 중에는 그 처리가 끝난 뒤 개입할 수 있다.

`accepted`는 브라우저 기본 동작 검사와 PM 검수를 마쳤다는 뜻이다. `delivered`는 대표가 요청한 반영 처리까지 마쳤다는 뜻이다. 두 상태 모두 검증된 사업 성과 수를 늘리지 않는다. 종료 요약은 비서의 보고 이벤트로 남긴다. 이는 다른 채팅·메일 발송이나 상주 비서 실행이 아니며, 예약 실행·여러 PM 운영·공개 홈페이지 개발·SNS 게시를 활성화하지 않는다. 실제 검사·실행 확인 범위는 별도 검증 기록을 따른다.

`python server.py` 실행 후 `http://127.0.0.1:8765/`에서 직원을 선택하고 자연어로 업무를 맡긴다. 직원 상세에서 기억과 활동·결과를 보고 업무 상세에서 중지·재개·수정 지시·담당 변경을 조작한다. 실제 제출은 구독 사용량을 소비한다.

음성 입력은 별도 버튼으로 `/voice/`를 연다. 원음과 화자 특징은 기기에서 처리한다. 인식 후 마이크를 끄며, 가져오기 버튼은 텍스트를 같은 탭의 조직 입력창으로 옮긴다. 업무를 맡기기 전에는 LLM 실행을 시작하지 않는다. 음성 등록·실제 목소리 정확도·Fold4 검증 범위는 [VOICE.md](VOICE.md)를 따른다.

API 필드와 상태 전이는 [ORG-CONTRACT.md](ORG-CONTRACT.md), 검증 결과는 [ORG-VERIFICATION.md](ORG-VERIFICATION.md)를 참조한다.
