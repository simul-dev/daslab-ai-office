# DAS Lab AI Office — 미션과 결과 중심 설계

수정: 2026-09-24. 대표는 자연어로 일을 맡기고 결과와 필요한 결정만 받는다. 세부 명세 작성과 처리 순서 판단은 내부 책임이다.

## 사용자 흐름

1. 한 입력란에 미션을 적고 맡긴다. 참고 자료는 선택 사항이다.
2. 내부에서 제목·사업 분류·우선순위·난이도·처리 순서·완료 기준을 정리한다. 코드 기반 초기 분류를 실제 AI 작업자가 다시 판단한다.
3. 실행 가능하면 시작한다. 실행 중인 미션이 있으면 대기열에 보존하고 우선순위에 따라 이어서 처리한다. 연결 문제·한도 때문에 시작하지 못하면 이유를 표시한다. 시작 전 대기 미션은 15초마다 다시 확인하므로 서버 재시작·연결 복구·일일 한도 해제 후에도 자동으로 시작한다. 실패했던 실행은 자동 반복하지 않는다.
4. 대시보드에서 달성 여부·기준 충족률·실제 실행 시간·결과 요약·남은 일을 확인한다. 상세 보고, 근거, 내부 기록은 선택적으로 펼친다.
5. 기본 검증을 통과한 달성 보고는 자동 완료한다. 부분 달성·막힘은 그 상태로 보고한다. 상시 승인 절차는 없으며 수정할 점이 있을 때만 의견을 적고 다시 맡긴다.

## 실행 상태와 성과 판정

실행 상태와 미션 성과는 별도다. `queued`는 대기, `running`은 실행 중이며, 새 미션은 검증을 통과한 달성 보고를 `completed`로 자동 완료한다. `review`는 보고가 저장된 상태로 사용하며 사용자의 필수 승인 대기를 뜻하지 않는다. 실행 실패와 취소는 `failed`, `cancelled`에 기록한다. 호환용 승인 API로 `completed`가 된 과거 미션도 성과 판정은 별도로 표시한다.

보고의 `outcome.status`는 `achieved`(달성), `partial`(부분 달성), `blocked`(막힘)이다. 기존 보고나 실행 중인 미션처럼 판정 근거가 없으면 확인 전으로 표시한다. 실행이 끝났다는 이유만으로 달성을 추정하지 않는다.

초기 완료 기준에는 미션 원문에서 요청한 결과를 보존한다. 사실 구분·정직한 보고 같은 품질 요구는 제약으로 두며, 사용자가 그 자체를 요청한 경우 외에는 달성률에 산입하지 않는다.

완료 기준마다 `met / unmet / unknown` 판정과 산출물 근거를 남긴다. AI는 실제 요청한 결과를 `milestones`의 세부 산출물로 나눌 수 있다. 각 항목은 원문 `criterion`, 세부 결과명 `deliverable`, `status`, `artifact_section`, `explanation`을 포함한다. 세부 항목은 원문 기준을 모두 포함하고 결과명이 중복되지 않아야 한다. 원문 기준의 판정은 그 세부 항목의 집계와 같아야 한다.

세부 항목이 있으면 달성률은 `floor(met 항목 수 / 전체 세부 항목 수 × 100)`, 없으면 완료 기준에 같은 산식을 적용한다. `unknown`이 하나라도 있으면 `null`로 남긴다. 항목은 동일 비중이며 실제 업무량·투입 시간·사업 성과 비율은 아니다. 모든 기준과 세부 항목이 `met`이고 보고가 `achieved`이며 코드 검증도 통과해야 자동 완료한다.

소요 시간은 저장된 실행 시작·종료 시각으로 계산한 실행별 시간을 합산한다. 대기 시간은 제외하며 실행 중인 회차는 현재까지의 경과 시간을 더한다. 서버 중단으로 종료 시점을 알 수 없는 회차가 있으면 합산 시간도 확인 전으로 남긴다. 재지시해도 이전 실행과 보고·의견을 보존한다.

## 구현 구조와 범위

Python 표준 라이브러리 HTTP 서버, SQLite, HTML/CSS/JavaScript로 구성한다. Planner / Worker / Reviewer는 Protocol과 provider 레지스트리로 분리되어 교체할 수 있다.

현재 Worker는 제공 자료를 바탕으로 문서·분석·코드 제안을 작성한다. 외부 검색·파일 탐색·셸 실행·추가 작업자 호출·저장소 수정·실제 프로그램 검증·외부 발송·구매·배포를 수행하지 않는다. 실제 행동이 필요한 미션을 계획만으로 달성했다고 보고해서는 안 된다. 손실을 막는 데 필요한 결정과 부족한 자료만 알리고 사소한 형식·표현은 스스로 정한다.

CodeReviewer는 실제 CLI 종료·완료 이벤트, 응답 구조, 파일, 기준별 근거와 참조 위치, 달성률의 일관성을 검사한다. 보고 내용의 진실성이나 고객 검증을 독립적으로 보증하는 심사자는 아니다.

ChatGPT에 로그인한 로컬 Codex만 사용하며 API 키 과금으로 전환하지 않는다. 기본 제한은 동시 실행 1개, 미션당 3회, 한국 날짜 기준 하루 10회, 회당 600초다. 실패·취소한 실행은 자동으로 재실행하지 않는다. 서버 재시작 시 실행 도중 중단된 미션은 실패로 복구하고, 아직 시작하지 않은 대기 미션은 자동 시작 대상으로 유지한다.

## 주요 API

| 요청 | 역할 |
| --- | --- |
| `POST /api/missions` | `{mission, inputs?, project_id?}`로 등록과 실행 요청. `{task, started, run?, start_error?}` 반환 |
| `GET /api/tasks` | 미션 목록과 `task.overview` 요약 |
| `GET /api/tasks/:id` | 미션·실행·이벤트·의견과 읽기 쉬운 `report` |
| `POST /api/tasks/:id/run` | 저장된 대기 미션의 시작 또는 명시적 재실행 |
| `POST /api/tasks/:id/cancel` | 실행 또는 대기 취소 |
| `POST /api/tasks/:id/revise` | `{note}`로 보완 지시와 재실행을 함께 요청. 즉시 실행하지 못하면 요청을 보존하고 실행 가능한 미션은 대기열로 이동 |
| `POST /api/tasks/:id/review` | 기존 승인·반려 API 호환 유지 |
| `GET /api/runs/:id/files/:name` | 허용된 보고서·내부 기록 조회 |
| `GET /api/health` | 연결 상태·실행 제한·현재 사용 현황 |

기존 `POST /api/tasks`의 구조화 입력은 호환용으로 유지한다. 사용자 화면에서 해당 항목을 모두 채우도록 요구하지 않는다. 쓰기 요청은 동일 출처에서 `Content-Type: application/json`, `X-DAS-Office: 1`을 사용한다.

## 저장과 검증

`data/office.sqlite3`에 미션·실행·이벤트·의견을, `data/runs/<task>/<run>/`에 입력 스냅샷·프롬프트·보고서·근거를 보존한다. JSON은 내부 저장 형식이며 기본 화면은 한국어 요약과 읽을 수 있는 보고서를 사용한다. 출처·기록 시각·프로젝트·검증 상태도 보존한다.

검증은 AI를 호출하지 않는 단위 테스트와 브라우저 확인으로 진행한다. 과거 실제 Codex 1회 실행 기록은 [VERIFICATION.md](VERIFICATION.md)에 있으며 새 흐름의 실제 AI 실행 성공을 뜻하지 않는다.
