# Organization API contract

This file describes the executable organization engine, separate from the legacy office database. All timestamps are UTC ISO strings; the UI displays Korean local time. No API key or automatic paid fallback. Staff records persist; only a queued mission starts an execution. The initial router is deterministic keyword routing. The bounded PM workflow below adds planning and review decisions for `office-ui`; it is not a general multi-PM conversation. Temporary subagent spawning and recurring duties are not implemented.

## Routes and responses

- `GET /api/org` → `{revision, employees, missions, events, execution, metrics}`.
- `GET /api/org/missions/:id` → `{revision, mission, attempts, events, children}`. `children` contains mission views assigned by this parent workflow, or an empty list.
- `POST /api/org/missions` body `{text, employee_id?: 'assistant', request_id}` → `{revision, mission, duplicate}`. `request_id` is required, nonempty max 160 chars. Reusing it with different text or employee raises Conflict.
- `POST /api/org/missions/:id/action` body `{action: 'pause'|'resume'|'cancel'|'instruct'|'reassign', text?, employee_id?}` → mission detail. Instruct needs text; reassign needs employee_id.
- `POST /api/org/employees/:id/memory` body `{text}` → `{memory, revision}`.
- `POST /api/org/connection` → `{available, message, checked_at}` after a manual login probe. It does not reveal credentials or claim remaining subscription quota.

## Snapshot

`employees`: owner, assistant, das-pm, das-rd, das-mkt, das-sales, each `{id, parent_id, manager_id, name, role, mandate, kind, status, current_mission_ids, current_mission, last_activity_at, memory_count, memories, metrics}`. `kind` is owner / assistant / pm / specialist. Owner status is `supervising`. Others idle, queued, running, waiting, pausing, paused, blocked, failed, deferred, review. `current_mission` is a concise mission object or null. `memories` is latest 12 items; fields `{id, employee_id, text, source, created_at, verification}`. Source is project path, owner, or mission ID; verification is `source_record`, `owner_statement`, `ai_unverified`, or the bounded `pm_review_and_browser_smoke` record described below. `metrics`: `{assigned, active, reports, verified_outcomes, interventions, execution_seconds, execution_time_unknown}`; verified_outcomes remains 0 until actual independent validation exists. Reports and execution time belong to the employee on the immutable execution attempt, not whoever currently owns the mission. Reassigning work does not transfer prior credit. While stopping an old attempt, its original employee remains shown as pausing.

`missions`: latest 100, newest first. Fields `{id, title, text, employee_id, requested_employee_id, accountable_id, status, status_label, priority, complexity, routing, created_at, updated_at, started_at, ended_at, elapsed_seconds, elapsed_unknown, attempts_count, intervention_count, last_activity, error, summary, outcome, progress_percent, progress_basis, verification, report, accomplishments, remaining, limitations, instructions, acceptance_criteria}`. `routing` string explains rules. `outcome` is `unknown` until structurally checked result, then AI self-assessed achieved/partial/blocked; `verification` is `not_verified`, `structural_only`, `delivery_receipt`, or `pm_review_and_browser_smoke`; the latter two describe the specific checks below, not business success. Progress is null unless a structurally consistent final self-assessment exists; it is never an elapsed-time percentage. `report` list `{title,content}`, `instructions` list `{text,created_at,source}`. `elapsed_seconds` totals known attempts and includes the current running attempt. `elapsed_unknown` is true when an interrupted run has unknown duration; do not present the known subtotal as the complete time. A restarted interrupted attempt has `duration_seconds:null`, no invented finish time, and a separate `recovered_at`.

Mission `status`: queued, running, waiting, pausing, paused, cancelled, completed, review, accepted, delivered, blocked, failed, deferred. Review means a report is ready and its substantive claims are unverified, not a mandatory owner approval gate. Waiting means a PM parent is waiting for an assigned child. Accepted means PM review and a browser smoke check passed; delivered means the requested file/Git operation completed. Neither is a verified business outcome. Completed is reserved for verified outcomes and is not issued by the structural reviewer. `status_label` supplies Korean text. During an active pause/cancel/instruct/reassign the mission is `pausing`; final cancellation is acknowledged only after the worker stops. Instruct/reassign stops the old attempt and holds it paused. Resume creates a fresh attempt using retained report/instruction context; it does not seamlessly modify a live LLM call.

`events`: latest 80, newest first; each `{id, type, message, employee_id, mission_id, created_at}`. Engine lifecycle and actual Codex thread/turn/item-completed events are stored. Token deltas, raw model payloads and reasoning text are omitted. Analysis runs have no external/file/shell tools. Scoped UI development emits actual file and command events; no tool activity is invented.

`execution`: `{provider:'codex', billing:'subscription', concurrency_limit:1, active_count, active_employee_id, queued_count, daily_limit, daily_used, remaining_quota:null, quota_message, quota_blocked, connection, capabilities, paid_fallback:false, recurring_enabled:false, temporary_agents_enabled:false}`. `connection`: `{available:null|boolean, message, checked_at}`; checked only when executing or by explicit connection refresh, never a blocking auth probe on snapshot. Daily cap uses the Korean calendar and counts actual organization attempts plus recorded legacy runs in the same data folder when available. Observed provider quota failures persist a dispatch suspension and defer queued/new missions; an explicit resume clears that suspension for another attempt. Login refresh does not prove a quota reset.

`metrics`: `{employees, active, queued, reports, verified_outcomes:0, interventions, execution_seconds, execution_time_unknown, attention}`. Reports count structurally checked reports including prior attempts, not independently verified business results.

`attempts` in detail: chronological `{id, mission_id, employee_id, number, status, started_at, ended_at, duration_seconds, error, verification, summary}`. Execution paths/credentials are not exposed.

## Scoped organization UI development (2026-09-30)

Submit and instruct optionally accept `context: {project_id: 'office-ui'}`. The server supplies trusted project details and rejects unknown project IDs; arbitrary client source paths are discarded. Idempotency includes project context. Design/edit intent with this context selects scoped development; analysis remains restricted. Only employees allowed by `config/development.json` (DAS-PM and DAS-RD) can execute or receive development work. With managed PM disabled, assistant intake routes this work to R&D and explicit PM selection remains PM-owned execution. With it enabled, assistant/PM intake uses the bounded workflow below; explicit R&D selection still uses `execution_mode: 'development'`.

The worker receives a separate `run_dir/workspace` with UI files and brand references. File/shell tools use a workspace-write permission profile, network disabled, native Windows sandbox explicitly enabled. Operational files are outside the write workspace. A successful static check records `delivery` with changed files, hashes, checks, `ready`, `attempt_id`, `preview_url`, `browser_verified: false`, and `applied_to_live: false`. A valid ready delivery is report-ready, not independently verified business success. Further instructions/reassignment/resume move the prior delivery to `previous_delivery`.

`GET /previews/:attempt_id/` redirects to an isolated loopback preview. It requires a stored verified artifact hash match, including after server restart. Preview only serves allowlisted static files, read-only organization data and events; mutation requests return 405. Main UI shows employee capabilities and the registered current edit target. Preview HTML includes an explicit read-only banner and disables controls that would submit work.

## Execution lifecycle

### Preview continuation and delivery

Submit accepts optional `source_attempt_id` for a verified `office-ui` development attempt. Source artifact hashes and project provenance are pinned and rechecked before execution. A clear continuation request may select the only available preview; ambiguous requests fail before model execution. New unrelated design requests do not inherit a preview. `preview_available` is independent from mission status: a ready preview never replaces `blocked` or its summary.

Submit also accepts `delivery_operation: 'apply'|'commit'|'push'`. Explicit handoff wording with `office-ui` context can infer that operation. Negative/explanatory requests do not infer authority. Delivery requires a pinned preview and the configured developer/delivery policy. An explicit payload operation uses `execution_mode: 'delivery'`; natural assistant/PM requests use the managed review path when enabled. The actual delivery uses the same serial dispatcher without a model call and records `release` receipts, including partial progress on failure. Source/operation changes under a reused request ID conflict. Receipt retries preserve the owned commit. Direct delivery success is `status: 'delivered', verification: 'delivery_receipt'`; failure is `blocked`. Neither increments verified business outcomes. Browser verification is a separate receipt and is not implied by direct delivery. Delivery attempts do not consume the AI daily-run budget. Active Git processing rejects interventions until its current operation finishes.

### Bounded PM workflow (2026-09-30)

`config/development.json.managed_pm` contains `enabled` and `max_revisions` (clamped to 0–2). When enabled, assistant/PM scoped development or natural delivery requests use `execution_mode: 'managed'` with `employee_id: 'das-pm'`. Original owner text, instructions and delivery authority stay on the parent. A new development request starts in planning; a pinned existing-preview delivery request starts with a browser check. The coordinator serializes PM decisions, DAS-RD development and trusted delivery; it does not create Codex chats or temporary staff.

Parent `workflow` fields:

- `stage`: `planning`, `working`, `checking`, `reviewing`, `delivering`, or `done`. A blocked/paused parent retains the resumable stage; blocked history entries are distinct from the saved next step.
- `round`, `max_revisions`, `decision_count`: revision count and execution bounds, not business progress percentages.
- `child_ids`, `current_child_id`: durable child mission identities; children have `parent_mission_id` and execution mode `development` or `delivery`.
- `history`: entries `{at, stage, summary}`; `work_criteria` and `review_summary` preserve the PM's work and review decisions.
- `browser_verification`: null or `{status, kind, url, started_at, elapsed_seconds, artifacts, checks, errors, screenshots, summary, scope, aesthetic_acceptance:false, business_acceptance:false}`. Optional `browser` records engine/channel/version. `checks` are `{name, status, detail}` entries; status may be passed, failed or skipped. Receipt status is passed, failed or unavailable. Screenshots are local execution evidence paths; no screenshot-serving API is added.
- `accepted_source`: the validated source provenance accepted for delivery. A delivery child pins `required_browser_artifacts` and rechecks the parent's authority, accepted source, passed receipt and artifact hashes before touching operating files.

PM decisions use read-only `execute_decision` with a fixed schema (`delegate`, `accept`, `revise`, `blocked`). A decision never extends tool or delivery authority. The server refuses completion without a passed browser receipt for the current source. Browser checks use a temporary isolated Chromium context, read-only loopback preview requests and bounded runtime. Missing optional browser tools block the workflow rather than fabricate a pass. The smoke checks cover listed UI interactions, not visual design acceptance or customer outcomes.

Managed success has `verification: 'pm_review_and_browser_smoke'`, status `accepted` or, after authorized delivery, `delivered`; `outcome` remains unknown and verified business metrics stay zero. A PM memory records this verification level and an `assistant.report` event records the final report, without sending an external message. The snapshot exposes `execution.managed_pm_enabled`. PM decision attempts count toward the AI daily cap; `browser_check` and `delivery` attempts do not. Parent elapsed time includes its child attempts.

Parent pause/cancel stops queued or executing child work with it. Instruct saves the new owner instruction, pauses work and replans on explicit resume; delivery instructions update or withdraw delivery authority. Managed reassign and direct child actions are rejected: interventions address the parent. Resume continues the retained stage or paused child and preserves partial delivery receipts. Restart recovers waiting parents and queued/running children as paused. No scheduler or silent restart is added. The UI hides child missions in the main list and shows them inside parent details.

One event-driven dispatcher serializes actual execution. Submit/resume signals it; no polling scheduler. Reopen recovers queued/running/waiting/pausing missions as paused (interrupted runs recorded); no silent re-execution. Resume is explicit after a quota block, error, pause, or interrupted server. Source knowledge, role, latest employee memories, retained mission report, and owner interventions go into each attempt. Pause/cancel use the existing worker cancellation signal. Independent proof of business outcomes is absent; structural checks never count as verified employee success.

API-key or Anthropic auth-token environment variables block execution before any provider probe or run; their values are never logged. The official CLI still enforces ChatGPT login and uses its existing restricted tool configuration. The production server disables legacy write routes and its old polling scheduler, so the old and new executors cannot compete for the subscription slot.
