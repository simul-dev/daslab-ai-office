# DAS Lab 공급망 DES 초안

합성 데이터로 주문 도착 → 재고 할당 → 피킹 완료, 재주문 → 입고를 비교한다.
시간 단위는 일이며 실고객 데이터·지도·공인 검증 모델이 아니다.

model.js는 시드가 고정된 주문 도착과 사건 목록으로 동작한다. 창고 재고,
대기 주문, 작업 중 주문을 분리하며 기말 미완료 주문을 완료 주문으로 세지 않는다.
주문 하나는 제품 한 개, 피킹 시간과 보충 리드타임은 고정이고 운송·비용은 미포함이다.
3D 장면이나 에셋이 아닌 단순 SVG 도식이며 실제 계산 결과와 연결한다.

허용 파일: README.md, index.html, style.css, model.js, app.js, model.test.cjs.
설치·외부 패키지·네트워크·외부 파일·운영 서비스 수정·배포는 범위 밖이다.
실제 개선 시 이 가정과 문제정의, 변경 이유, 실행한 검증·못 한 검증을 갱신한다.

브라우저에서 model.js의 DASModel.checks()가 재현성, 재고·주문 보존,
무수요, 재고 부족, 피킹 용량 대안의 시나리오를 실행한다. 초안 코드의 자체
검사는 독립 검증이 아니다. 서버 finish는 문법·범위만 검사하며 model.test.cjs를
호스트에서 실행하지 않는다. 기준 입력과 기대 결과의 외부 검토가 별도로 필요하다.

## 유지해야 하는 검사 계약

window.DASModel.run(input)는 순수하고 결정적인 계산이며 defaults와 checks()를 함께
제공한다. 입력은 days, ordersPerDay, initialStock, reorderPoint, batch, leadTime,
servers, serviceTime, seed 숫자다. batch=0은 보충 중지이고 ordersPerDay=0도 허용한다.
출력 키는 parameters, arrivals, completed, backlog, inService, stock, received,
allocated, incoming, completionRate, meanOrderDays, invariants를 유지한다.
재고 보존: initialStock+received=stock+allocated. 주문 보존:
arrivals=completed+backlog+inService. allocated=completed+inService.
관측기간의 arrivals=days*ordersPerDay이며 모든 개수와 평균 시간은 0 이상이다.
기말 미완료 수요를 완료율·평균 완료 시간의 완료 주문에 포함하면 안 된다.
DOM #model-form, #run-model, #model-results, #model-checks, #model-scene와
#days/#orders/#stock/#reorder/#batch/#lead/#servers/#service/#seed 입력을 보존한다.
결과 요소의 data-status/data-completed/data-backlog, 검사 목록의 data-status를
실제 실행 결과에 맞춘다. 검사 통과를 하드코딩하지 않는다. 원래 DES 문제와 계약을
바꿔야 하면 기존 검증을 통과했다고 주장하지 말고 변경 필요성과 새 검증 기준을 보고한다.

## 정책 비교 v1 · 2026-09-30 실제 구현

문제: 입고 지연 때 안전재고 증가와 긴급운송 전환의 납기·비용 절충을 같은 외생 조건에서 비교한다. 위의 기존 `run/defaults/checks` 및 DOM 계약은 그대로 유지한다. 기존 SVG는 피킹 완료 기준의 별도 모형이며 새 비교 결과와 동일한 결과가 아니다.

### 선택한 모형과 대안

14일 단일품목 이산사건 모형(DES)을 채택했다. 주문·예약·출하·배송·발주·입고 기록을 남겨 보존식과 비용을 재계산하기 쉽다. 일별 집계 방식은 구현이 단순하지만 예약/배송의 기간 경계와 시간적분을 잃으므로 보류했다. 에이전트 기반 모형은 개별 업체의 협상·적응 자료가 없고, 시스템 다이내믹스는 주문별 OTIF 추적 목적에 맞지 않아 이번 범위에서 사용하지 않았다. 60일 확장·다품목·실제 도로·3D는 구현하지 않았다.

### API와 지원 범위

`DASModel.comparePolicies(input={})`는 입력을 변경하지 않는 결정적 함수다. 반환: `parameters, demandTrace, shockTrace, policies`. 정책은 정확히 P0/P1/P2 순서이며 각 정책에는 주문, 발주, 실제 입고, 모든 상태 전이, 지표, 비용이 있다. `policyDefaults`와 별도 `policyChecks()`도 제공한다. 기존 `checks()`만으로 정책 비교를 검증했다고 보지 않는다.

| 입력 | 기본 | 지원 범위 (정수) |
| --- | ---: | --- |
| days | 14 | 1–30일 |
| ordersPerDay | 6 | 0–100건/일 |
| initialStock | 12 | 0–10000개 |
| seed | 42 | 1–999999 |
| safetyStockDays | 2 | 0–10일분 |
| emergencyCapacity | 6 | 0–100개/일 |

범위 밖·소수·문자·null·비유한 수·미지원 키는 거절한다. 수요는 매일 정해진 건수의 시드 기반 도착 시각으로 생성한다. 주문당 1개, 납기는 도착+2일. 수요 난수와 지연 난수의 스트림을 분리하고 정책 실행 전에 모든 외생 조건을 만든다. 정책 행동은 다른 정책의 수요·지연을 변경하지 않는다.

### 재고·사건·정책 가정

- P0 목표는 하루 수요×3. P1은 여기에 하루 수요×safetyStockDays를 추가한다. P2는 P0 목표를 쓰며 지연이 예고된 발주에서만 최대 emergencyCapacity를 긴급 전환한다. 매일 1회 검토하므로 긴급 용량은 일별 한도다. 추가 긴급 발주는 만들지 않는다.
- 매일 정수 시각 0…days−1에 목표와 재고위치의 양수 차이를 발주한다. 정규 출발은 발주+0.5일, 입고는 발주+2일+지연이다. 발주일 2…7에는 3일 지연, 나머지는 별도 시드 스트림으로 0 또는 1일 지연이다. 긴급 전환은 발주 시 정규 출발 전에 결정한다. 긴급 출발은 +0.25일, 입고는 +1일이다. 공급 지연을 사전에 알고 긴급편은 지연되지 않는다는 합성 가정이다.
- FIFO 예약, 예약+0.25일 출하, 출하+0.5일 배송. 피킹·배송 처리 용량은 무제한이다. 예약 시 물리재고를 줄이지 않고 출하 시에만 줄인다.
- onHand는 예약 포함 물리재고, backlog는 미예약 대기만 의미한다. `inventoryPosition=onHand-reserved+onOrder-backlog`. 예약 주문을 backlog에서 다시 빼지 않는다. `initialStock+received=onHand+shipped`.
- 같은 시각 사건 순서: 입고 → 배송 완료 → 출하 → 수요 도착 → 일별 발주 검토. 동종 사건은 등록 순서. 입고/수요 도착 직후 예약을 수행하며 각각 로그를 남긴다. 시각 0의 변경 전 초기 상태와 시각 days의 종료 상태를 포함한다. 종료 시각과 같은 사건까지 처리하고 그 이후는 미완료로 남긴다.
- 정규 실제 입고량은 발주량−긴급 전환량이다. 운송 방식별 실제 입고를 최대 한 번 기록하며 관측기간 밖 입고를 receipts에 넣지 않는다.

### 지표와 합성 비용

OTIF는 기한 내 배송 완료/전체 유입 주문이며 기말 미완료도 분모에 포함한다. 무수요는 0. 평균 소요일은 배송 완료 주문만 대상으로 한다. holdingUnitDays는 stateLog의 onHand를 시간 적분한 개·일이다.

합성 화폐 CU를 사용한다(원화·고객 견적 아님). 보유 단가 0.1 CU/(개·일), 정규 운송 1 CU/개, 긴급 운송 4 CU/개, 발주비 2 CU/건. 운송 비용은 발주된 정규/긴급 물량으로 계산하므로 기말 미입고도 포함한다. 총비용은 보유+정규+긴급+발주비. 구매원가·품절 벌금·반품·차량 배차 비용은 제외한다. 특정 정책의 우위는 하드코딩하지 않았다.
